Open Source · Case Study

FailLoud

v0.4.0 · MIT

A verification harness for LLM agent outputs — it catches the silent failures agents ship as “done.” Run it as a CLI in a pipeline, or as an MCP server your agents call before they are allowed to claim success. The core is standard-library-only Python: a verification tool should add no supply-chain surface of its own. And since v0.2.0, every verdict can be sealed into a hash-chained receipt — so what carries a result downstream is an audit trail anyone can re-verify, not the agent’s word. New in v0.3.0: watch mode polls a pipeline’s output file or directory and re-verifies each output the moment its content changes, sealing every verdict to the chain automatically. New in v0.4.0: a LangChain adapter verifies outputs in the loop — a callback handler checks each LLM and chain result as it finishes, before the next step builds on it.

FL001

Placeholder shipped

Output declared done while its payload is empty or still carries template scaffolding — lorem ipsum, unrendered {{braces}}, “coming soon.” Nothing crashes; every signal says success.

FL002

Unbacked claim

The agent says it sent, posted, published, deployed — and nothing in the output backs the claim: no ID, no URL, no receipt, no artifact. A claim without evidence is a rumor.

FL003

Stale state

The run worked from a context snapshot older than you allow — or the state it planned from and the state it carried disagree on version. Confident work, expired world.

FL004

Count mismatch

The headline number disagrees with the itemized record underneath it — reported 12 delivered, the list holds 9. Only the list was ever true.

FL005

Missing components

Required parts are present but empty, a segment occupies its slot and contains nothing, and the deliverable goes silent where content should be.

THE VERDICT

Fail, warnings, or pass

Every check produces located findings — JSON path, severity, and a message written for the failure report — rolled into one verdict: FAIL, PASS WITH WARNINGS, or PASS.

terminal — failloud check
$ failloud check examples/failing_output.json

FL001  placeholder_shipped   ERROR    $.output.body
       Placeholder content shipped as final: 'coming soon', 'lorem ipsum', '{{ }}'.
FL002  unbacked_claim        ERROR    $.claims[1]
       'card_published' claimed — no id, URL, receipt, or artifact backs it.
FL003  stale_state           ERROR    $.state.context_updated_at
       State is 77.1h old (limit 24h); planned from v9, carried v7.
FL004  count_mismatch        ERROR    $.counts.delivered
       Reported as 12 — the itemized record contains 9.
FL005  missing_components    ERROR    $.segments[2]
       Zero-length segment, and a 5.5s dead stretch where content should be.

VERDICT: FAIL — 8 errors, 1 warning. The corrected output passes clean.

Built from real production failures. Every check in FailLoud exists because a real system failed that way in production — and the failure was only visible to whoever finally read the output itself. The failures became rules; the rules became this tool.

Production Lessons

Rules I now enforce everywhere

Each of these was learned the expensive way — from a failure that no dashboard caught. They are the same lessons FailLoud automates.

“Live” is a reading, not a log line.

A launch was marked complete while the page itself still carried placeholder copy. The URL was public, the pipeline was green, and every automated signal said success. The failure was visible only to a human who actually read the page.

The RuleVerify the artifact itself, never the success message. Nothing is live until the live thing has been read.

Sent is not delivered.

A batch of messages was reported as sent. One address had bounced — and nothing downstream ever knew, because “sent” was asserted by the same component that performed the send, and nothing demanded proof.

The RuleCount delivered, not sent. A claim of a completed action needs evidence attached — or it is a rumor.

If it isn’t written state, it doesn’t exist.

A handover lived in a conversation instead of durable state. The next step rebuilt its understanding from a summary of a summary — then acted on it with full confidence.

The RuleHandovers are built from written state and traces, never from what someone remembers saying in chat.
